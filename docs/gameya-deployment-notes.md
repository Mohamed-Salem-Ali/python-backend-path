# Gameya deployment notes

These notes are the reference for deploying the Django Gameya project, and for describing the deploy in your portfolio, CV and case study. The steps are in [module 12](../django/12-deployment/lesson.md) and the [deploy checklist](../django/12-deployment/deploy-checklist.md). This page holds the facts those steps depend on, in one place. It belongs to the [12-week plan](12-week-plan.md): the week 9 checkpoint is "Gameya runs in production on Django."

## Settings on Render

Set these in the Render dashboard. The blueprint, `render.yaml`, records the names and the generated key. It never holds a value that must stay secret.

| Variable | Value | What it does |
|---|---|---|
| `PYTHON_VERSION` | `3.12.6` | The Python version the build uses |
| `DJANGO_PRODUCTION` | `1` | Switches on the production settings from module 11 |
| `DJANGO_SECRET_KEY` | Generated by Render | Signs the JWT login tokens and the other values Django signs. In production, the app raises an error at startup without it |
| `DJANGO_ALLOWED_HOSTS` | The service host, such as `gameya-xxxx.onrender.com` | The host names Django accepts. Separate several with commas. A wrong value makes every request fail |
| `DATABASE_URL` | Copied from the PostgreSQL service in the same region | Points the app at PostgreSQL. Without it, the app uses its SQLite file, which a redeploy can lose |
| `DJANGO_DEBUG` | `0` | Debug pages show tracebacks and settings. Set it to `0` on Render. If it is unset, the settings default to on |

The build command and the start command are in [section 2 of the checklist](../django/12-deployment/deploy-checklist.md#2-render-settings-fill-in-once-check-on-each-deploy). Use the same text in the dashboard, so the two agree.

## Decisions to name in the case study

Each decision below has a cost. Module 13 asks for two in the case study, so pick the two that matter most to you.

- **PostgreSQL on Render, not SQLite on the server.** It costs one more service, and the free database expires after a period that Render sets.
- **gunicorn, not `runserver`.** It runs several worker processes, so check the logs for both the migration and the listen line. gunicorn does not run on Windows, so the tests check its configuration, not its process.
- **WhiteNoise for static files, not a separate static host.** It needs no extra service, and the app serves its own files. A CDN is the next step if the static files become a bottleneck.
- **One web service, no worker.** The blueprint and the start command run one service. The weekly unpaid-payments report from module 10 does not run on Render unless a Celery worker and a beat scheduler run as their own services, with a broker.

## Known gaps to disclose

Say these in the portfolio entry, as a fix you made or as an open risk.

1. **Background work does not run on Render.** The web service runs no worker and no beat scheduler, so the weekly report does not run in production. Check the logs and the services list before you claim that it does.
2. **Open rows from the security review.** The payment view accepts a POST from anyone, which is row 15 of the [security review template](../django/11-auth-security/security-review.md). Login is not rate limited (row 16), and password reset is not tested (row 20). Copy the rows from your own `security-review.md`, and mark each one Pass, Fail or Open.
3. **The free plan.** A free web service sleeps after 15 minutes without traffic, and the first request after that is slow. Record the wait from the checklist. The free database's period is set by Render's terms, which change, so read them before you write a date.
